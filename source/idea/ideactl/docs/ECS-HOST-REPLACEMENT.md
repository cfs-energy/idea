# Replacing hosts created before the shared-storage mount correction

Updating the ECS launch template does not update running hosts. Before deploying application stacks on previously created capacity, deploy only the ECS capacity stack, then replace every host using the previous launch-template version. Do not resume the application upgrade until every active host passes the checks below.

Use manual replacement. A CloudFormation ASG rolling update does not provide the application-specific submission barrier, PBS inventory check, mount verification, or session checks required here. ECS managed termination protection protects hosts that carry tasks; bypassing it before draining would discard work. Keep managed termination protection and the ASG's default scale-in protection enabled throughout this procedure. AWS describes this behavior in [managed termination protection](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_AutoScalingGroupProvider.html).

1. Record the ASG's current minimum, maximum and desired capacity, launch-template ID and version, and all existing EC2 and ECS container-instance IDs. Deploy the ECS stack with the corrected template and verify the ASG references that version. Record which hosts still use older versions.
2. Add enough temporary ASG headroom and desired capacity for at least one replacement host. Account for placement constraints, task memory, CPU and network interfaces. Wait for the new host to be `InService`, ECS `ACTIVE`, and agent-connected. If the replacement does not become ready, stop and retain the old capacity.
3. On the replacement host, inspect cloud-init completion and `findmnt --target <mount-directory>` for every configured control-plane host bind mount. Verify filesystem type, remote source including the export path, mount options, and access from the application UID. An existing local directory is not proof of a mount. Check ECS registration happened after successful mount checks. EFS task volumes also need a task-level access check.
4. Before draining a host carrying the scheduler, enable maintenance using the cluster-manager ID from `global-settings.module_sets.<set>.cluster-manager.module_id`. Save its previous maintenance state. Require two empty PBS inventories at least 30 seconds apart after the write. Wait for running work to finish; do not delete jobs. For desktop services, arrange a maintenance window and finish or disconnect active sessions according to the deployment's operating procedure.
5. Mark one old container instance `DRAINING`. Wait for replacement service tasks to become healthy and for the old host to have no non-daemon tasks. Inspect task and service events, load-balancer health, and storage access. A single scheduler may stop before its replacement starts, so keep submission closed. Standalone tasks require explicit completion; draining does not migrate them. Stop if any workload cannot drain safely.
6. Wait for ECS to release that drained host's managed scale-in protection. Verify no non-daemon tasks remain immediately before retirement. Retire only that identified old instance through the ASG, without decrementing desired capacity. Never clear protection on an active host or disable protection for the whole group. Wait for the next replacement to pass steps 2 and 3 before proceeding to another old host.
7. Repeat until no host uses an older launch-template version. Confirm every application service is stable, the scheduler can query its job database, all expected mounts are remote filesystems, and no old container instance is active. Restore the original capacity bounds after verifying the retained capacity can run all services. Restore the saved maintenance state only when scheduler readiness is confirmed.

If a mount, task, or health check fails, leave submission closed, preserve the remaining old hosts, and repair the replacement before continuing. This procedure is a deployment prerequisite, not an automatic refresh triggered by a template update.
